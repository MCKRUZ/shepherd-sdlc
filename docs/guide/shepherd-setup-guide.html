0. What Shepherd is

Shepherd is two things that work as one. The plugin, shepherd, runs inside Claude Code: 32 slash commands (/sprd and /sprd-*), 14 agents, and a set of Python scripts that read and write a project's lifecycle state. The desktop app in studio/ is an optional Electron front end. It never reimplements plugin logic. Every fact it shows and every change it makes goes through the plugin's own scripts, run the way a person would run them.

The spine

0Discovery
1Requirements
2Design
3Foundation
buildBuild loop
7Documentation
8Deployment
9Monitoring
closeClose & Transfer

Phases 4, 5 and 6 do not exist. The batch Implementation, Quality and Testing phases are replaced by the continuous Build loop, where checking happens per change. The gated opening phases produce documents. The Build loop builds one spec at a time. The gated closing phases prove the system can be operated and handed over.

TermMeaning
GatesSeven checks at every phase transition: integrity, completeness, metrics, compliance, consistency, quality, exit criteria. Gates 1 to 6 pass or fail. Gate 7 always reads REVIEW: it shows the approver the phase's own exit conditions instead of deciding for them. Severities are MUST (blocks), SHOULD (warns), MAY (informs).
SpecsThe Build unit. One spec (specs/NNNN-name.md) = one branch = one pull request. A spec is built only when it clears the Definition of Ready. The spec lives in version control at the repo root, not under .sdlc/.
SprintsA two-week commitment window over the spec backlog. A named human slates a count of specs by risk-tier mix, readies the sprint when every spec is READY with Engineering and Data verdicts, and closes it with kept, carried or dropped. Sprints never gate and are never gated.
Honest numbersA value that was not measured reads "no data", never 0. Velocity, story points, estimates, effort, hours, PR count and lines of code are refused with exit 2. Nothing is aggregated per person.
Agent proposes, named human decidesThe agent drafts the slate, the risk tier, the carry/drop split. A named human confirms each one. A --by that reads as an AI is refused.

2. Install the plugin

From inside Claude Code, one marketplace add and one install. This brings the orchestration commands and the delivery harness payload.

/plugin marketplace add MCKRUZ/shepherd-sdlc
/plugin install shepherd@mckruz

The marketplace is named mckruz. Version 2.0.0 renamed the plugin to shepherd and its commands to /sprd-* (/sprd for the bare command); there are no aliases under the old prefix. A repository set up on an earlier version runs /sprd-upgrade, which brings the harness forward and rewrites the command names inside the auto-injected SDLC section of its CLAUDE.md, showing the diff first. Project state under .sdlc/ keeps its name and is read as before.

Developers working on the plugin itself clone it and symlink it as a skill instead:

git clone https://github.com/MCKRUZ/shepherd-sdlc.git
ln -s /path/to/shepherd ~/.claude/skills/shepherd   # macOS / Linux
mklink /D "%USERPROFILE%\.claude\skills\shepherd" "path\to\shepherd"   # Windows
cd shepherd/scripts && uv sync   # optional warm-up; uv run syncs on first use anyway

Verify

/sprd-doctor
What you should see

In a repository that has no .sdlc/ yet, the doctor stops and points at /sprd-setup: the harness is not installed, so there is nothing to check. That answer still proves the plugin's commands are loaded and uv can run its scripts. After §4 the same command prints one PASS / FAIL / WARN line per check with the fix attached. Exit 0 means no failures; exit 1 means at least one. /sprd-doctor --offline skips the checks that need gh or az.

3. Start the desktop app

Install a release (most people)

Download the installer for your machine from the repository's Releases page: the .dmg on macOS, the .exe on Windows. Each release is built by CI from a version tag, so the file name carries the plugin version it matches (Shepherd_2.0.0.dmg). The installers are not in the repository itself.

First launch of an unsigned build: on macOS right-click the app and choose Open, then Open again; on Windows choose More info → Run anyway on the SmartScreen prompt. A signed release has neither prompt. The app still needs Claude Code, uv and git on the machine (§1) and the plugin installed in Claude Code (§2): a packaged Shepherd finds the plugin in Claude Code's marketplace cache on its own.

Run from source (developers)

The app is a Node project inside the plugin repository. Everything runs from studio/, not the repository root.

cd shepherd/studio
npm ci
npm run dev

npm run build packages the app with electron-builder. npm test runs the unit tests; the integration tests also need the plugin's Python environment (uv run --project scripts pytest scripts/tests -q from the repository root) and fail loudly without it. Set STUDIO_SKIP_PLUGIN_TESTS=1 to run only the rest.

What you should see on first open

A window titled Shepherd. The Welcome screen offers New project…, Open folder… and a Recent list that starts empty ("No recent projects"). Before that screen, the app probes five tools: Claude Code, uv, the plugin's scripts/ folder, git, and the GitHub CLI. Each missing one appears as an amber notice, "<tool> wasn't found.", with the probe's own error, an Install instructions link, and a path field with Use this to point the app at a copy it did not find. The Azure CLI is probed only when a project's repository is on Azure DevOps and is never required to open a project. Nothing is installed by the app.

Settings › Tooling on this machine

Says which plugin drives this session and which Claude Code it found. Unpackaged, the app prefers <studio>/../scripts when it carries capabilities.py, then the newest marketplace-cached plugin under ~/.claude/plugins/cache/, then a path set in the app.

What you should see 
Claude Code   2.1.289 — accepts every flag Shepherd uses
Plugin        /…/shepherd/scripts — version 2.0.0, from the checkout beside Shepherd

On an older CLI the first line reads "Claude Code 2.1.239 lacks --permission-mode — update with claude update" and the model buttons are off until it is updated. The plugin line's origin is one of: the checkout beside Shepherd, the plugin cache, the path set in Shepherd.

4. Create or adopt a project

Script paths in this guide (uv run scripts/<x>.py) are relative to the plugin checkout root. The slash commands run the same scripts for you from ${CLAUDE_PLUGIN_ROOT}. You need the direct form only when you want JSON, or you are outside Claude Code.

4.1 /sprd-setup

Open Claude Code at the repository root and run:

/sprd-setup
  1. Profile. Pick one: microsoft-enterprise (.NET 10 + Angular 22 + Azure, SOC 2, 80% coverage, TDD), ado-enterprise (the same on Azure Repos + Azure Pipelines), ado-enterprise-python (FastAPI + React on Azure DevOps; asks PostgreSQL or Azure SQL), starter (no compliance gates), creative-tooling (Python/uv + pytest). Custom profiles are copied from profiles/starter/profile.yaml and validated with uv run scripts/validate_profile.py <profile.yaml>.
  2. Project name. Defaults to the directory name.
  3. .sdlc/ is created (init_project.py). Phase 0: Discovery is active.
  4. The delivery harness is installed (install_harness.py): governance CLAUDE.md, .claude/{settings,hooks,agents,skills}, the CI rails, infra/ starters, .mcp.json, and the install receipt .claude/harness-manifest.json. On GitHub that is 7 workflows in .github/workflows/ (5 rail gates + 2 eval). On Azure DevOps profiles it is Azure Pipelines under .azuredevops/pipelines/ with branch policies as code in .azuredevops/rails/. Existing files are left in place and reported SKIPPED.
  5. CLAUDE.md gains the SDLC section from the profile's template.
  6. Branch protection (optional). GitHub: bash scripts/rails/apply-branch-protection.sh. Azure DevOps: bash scripts/rails/configure-branch-policies.sh --dry-run, then without the flag. Either makes the five blocking checks (build-and-test, spec-gate, grader, correctness-review, security-review) plus a non-author approval mandatory at merge.
  7. Validation. validate_profile.py .sdlc/profile.yaml confirms the frozen profile.
What you should see 
SDLC + delivery harness installed!

Profile: <profile-id>
Phase: 0 — Discovery (active)
Harness: CLAUDE.md, .claude/, .github/workflows (7 workflows: 5 rails + 2 eval), infra/

Next steps:
1. Fill the {{PLACEHOLDER}} tokens in CLAUDE.md (stack, glossary, gated paths);
   on Azure DevOps, also replace ADO_ORGANIZATION_NOT_SET in .mcp.json
2. PROVE THE RAILS before trusting them — run the shakedown drills in .github/RAILS.md
3. Run /sprd to start the Phase 0 discovery interview
4. Run /sprd-gate when ready to check exit criteria; /sprd-next to advance

Then run /sprd-doctor again. It now checks the installed harness: hook interpreters, executable bits, the secrets or variable groups the gates read, the ruleset or branch policies. Commit .claude/harness-manifest.json with the rest.

4.2 What .sdlc/ contains

.sdlc/
├── state.yaml          # phase tracking: current phase, statuses, sign-offs, history
├── profile.yaml        # frozen copy of the selected profile
├── constitution.md     # project constitution
├── context/
│   └── layers/         # phase summaries (living, regenerated when sources change)
├── artifacts/          # one directory per phase slug (see §5)
├── reports/            # phase reports, sprint pages, index.html (local; not synced)
├── metrics/            # append-only JSONL ledgers: gates, specs, sprints, findings, decisions
├── sprints/            # SNN.md sprint records (created by /sprd-sprint new)
├── team.yaml           # optional roster (4.3)
├── code-host.yaml      # optional host pin (4.4)
└── decision-log.md     # DL-NN decisions with owner and 2-business-day clock

Specs live in specs/ at the repository root, beside the code, not under .sdlc/.

Adopting an existing codebase

Run the same /sprd-setup. Phase 0 detects a brownfield repository and generates a workspace analysis before the Discovery interview. A repository that already has .sdlc/ is warned about; /sprd-harness adds or refreshes only the harness, and /sprd-upgrade later upgrades it without clobbering local adaptations.

4.3 The team roster: .sdlc/team.yaml

Optional, but check_spec.py reads it: a spec whose owner or team is not in the roster is blocked. Without a roster that check is skipped and the report says so. Copy the worked example and edit it:

cp <plugin>/templates/team/team.example.yaml .sdlc/team.yaml
version: "1.0"

teams:
  - name: claims
    lead: "@priya-n"          # every team needs a lead whose roles include lead

people:
  - handle: "@priya-n"        # the roster key on every code host: ^@[A-Za-z0-9-]+$
    name: "Priya Nair"
    email: "priya.nair@example.com"   # optional; Azure DevOps sign-in identity (UPN), unique
    team: claims
    roles: [owner, developer, lead]   # roles this person MAY hold on a spec
    signs_off: ["1", "2", "build"]    # phase ids this person may sign
RoleMay hold
ownerAccountable for a spec's intent and decisions.
developerDrives the agent, approves the plan.
checkerThe non-author approval. Never the same person as the developer on one spec.
leadLeads a team; confirms risk tiers.
securityNamed sign-off on HIGH specs.

Validate, and add or update a person without hand-editing (comments and ordering survive):

uv run scripts/validate_team.py .sdlc/team.yaml
uv run scripts/set_setting.py --repo <path> person "@jordan-b" --name "Jordan Baptiste" --team claims --roles developer checker
uv run scripts/set_setting.py --repo <path> person "@jordan-b" --email jordan.baptiste@example.com

email: matters only on Azure DevOps, where a pull request names reviewers by sign-in identity rather than handle. It is the only bridge from a UPN to a handle. Nothing guesses it from a display name or the part before the @. A checker with no email is reported as an assignment_error at hand-off, not invented.

What you should see 
PASS — team.yaml is valid

4.4 The code host

The repository chooses its host by its origin remote. A GitHub remote uses gh; a dev.azure.com, *.visualstudio.com or ssh.dev.azure.com remote uses az. Confirm what was detected and whether its CLI answered:

uv run scripts/code_host.py --repo <path>
uv run scripts/code_host.py --repo <path> --json
What you should see 
Code host: azure-devops (from remote) — CLI: az [available]
  from origin https://dev.azure.com/contoso/Claims/_git/claims-api
  Remote: contoso/Claims/claims-api
  CI platform: azure-devops

The JSON form carries a top-level host block, {name, source, cli, cli_state, detail}, so a reader can see why a host was chosen; a remote block with org, project, repo, slug, web_url; and ci_platform. cli_state is one of available, not_installed, extension_missing, signed_out, or unknown when the probe could not run (--no-probe). Unknown is never read as no. The code host and the CI platform are two axes: GitHub + Azure Pipelines is a legitimate mix and is reported, never resolved silently.

Pin the host only when the origin is not recognised (GitHub Enterprise Server, an unusual proxy). The pin travels with the clone as .sdlc/code-host.yaml:

uv run scripts/set_setting.py --repo <path> code-host --host azure-devops
uv run scripts/set_setting.py --repo <path> code-host --host azure-devops --organization contoso --project Claims --repository claims-api   # when the remote cannot be parsed at all

Precedence, highest first: --host on any host-touching script, the SHEPHERD_CODE_HOST environment variable (or SDLC_CODE_HOST, the pre-2.0 name, still read), .sdlc/code-host.yaml, the parsed remote, the harness manifest as a tie-breaker when there is no usable remote, then none, which falls through to gh exactly as before.

5. The daily loop

Discovery, Requirements, Design and Foundation produce documents and are signed off one at a time. Then the Build loop runs until a human declares the feature set complete. Four commands carry the day.

CommandDoesWrites
/sprdGuidance for the current phase: what to do, which skills to use, which artifacts to produce, and a Team & RACI block naming who is Responsible, Accountable, Consulted and Informed this phase.nothing
/sprd-statusThe dashboard: current phase, progress, phase table with artifact counts and timestamps, recent transitions, open and overdue DL-NN decisions, a stale-artifacts line when a ledger exists.nothing
/sprd-gateRuns the seven gates for the current phase without advancing, then writes and opens the phase report..sdlc/reports/<slug>-report.html, a line in .sdlc/metrics/gate-log.jsonl
/sprd-nextRuns the gates; if every MUST passes, records a named sign-off, condenses the phase into its layer, and advances. Offers smart repair on fixable failures.state.yaml, .sdlc/context/layers/phaseN-name.md
/sprd
/sprd-status
/sprd-gate
/sprd-next
What you should see from /sprd-gate 
G1-integrity       PASS  [MUST]   3 of 3 required artifacts present
G2-completeness    PASS  [MUST]   no unfilled placeholders
G3-metrics         PASS  [SHOULD] file sizes within profile limits
G4-compliance      PASS  [MUST]   priorities labelled
G5-consistency     PASS  [MUST]   no locked metric drifted from a prior layer

6. Specs and sprints

6.1 Author a spec: /sprd-spec

/sprd-spec                                  # workflow mode: new spec in this engagement
/sprd-spec --spec specs/0007-name.md        # finish and re-check an existing spec
/sprd-spec --repo <path>                    # standalone: any repo with no .sdlc/

The command gathers Intent (Goal, Why, Scope in and out, Acceptance checks, silent decisions onto the Decision List, the one harness pattern this change reuses), proposes a risk tier for a human to confirm, scaffolds specs/NNNN-name.md with new_spec.py, and enforces the Definition of Ready with check_spec.py until the spec reads READY. Underneath, with the flags verified:

uv run scripts/new_spec.py --repo <path> --name "duplicate claim 409" --risk HIGH --source "FR-012" --owner @priya-n --team claims
uv run scripts/check_spec.py --spec <path>/specs/0001-duplicate-claim-409.md
uv run scripts/check_spec.py --spec <path>/specs/0001-duplicate-claim-409.md --state .sdlc/state.yaml   # also logs to .sdlc/metrics/spec-log.jsonl
What you should see 
Definition-of-Ready Check — 0001-duplicate-claim-409.md
==================================================
  READY   [MUST] name: duplicate-claim-409
  READY   [MUST] owner: @priya-n
  READY   [MUST] risk: HIGH
  READY   [SHOULD] harness context named
  READY   [MUST] owner '@priya-n' found in roster
  READY   [MUST] team 'claims' found in roster
  READY   [MUST] all required sections present
  READY   [MUST] in-scope stated
  READY   [MUST] out-of-scope stated
  READY   [MUST] 6 acceptance check(s)
  ADVISE  [SHOULD] Acceptance check may fail the vague-line test (no concrete signal (number, status code, quoted value, code, path)): "The user is told clearly..."
  READY   [MUST] no unfilled placeholders
  READY   [MUST] checking ladder depth matches tier (HIGH)
==================================================
READY (with 1 advisory note(s)) — review the vague-line flags before building.

MUST findings block. ADVISE findings are the vague-line lint: "could two people build different things from this?" Tighten the line with a status code, a count, a path, or accept it with a reason. The risk tier sets the Checking Plan depth mechanically: every tier blocks on CI, grader, correctness and a non-author approval; HIGH adds a security pass and a named sign-off. The status field (draft, ready, in-flight, merged) is hand-moved; no script writes it.

6.2 Run a sprint: /sprd-sprint

Different verbs belong to different moments in the two-week rhythm. Every example is in workflow mode; add --repo <path> instead for a repo with no .sdlc/state.yaml. --sprint defaults to the active sprint on every verb except new.

MomentVerbsWho
Setting up the next sprint (last week of the current one)new, slate, unslateProduct proposes and confirms the slate; /sprd-refine --sprint drives the specs to READY
Sprint planning meeting (day 0)ready; plan re-renders the pageA named human readies it; the team walks the page
Every daystatus (default)Anyone; /sprd-refine with no arguments for the agenda
Whenever work changes handshandoff, ackThe recorder and the recipient
Last daycloseA named human confirms every carry and drop; /sprd-retro for cross-sprint patterns
# 1. Create the record. End defaults to the last business day of a 10-business-day window (start is day 1).
/sprd-sprint new --sprint S07 --goal "Duplicate claims are refused with a 409 and a reason" \
  --start 2026-10-05 --target 6 --mix "HIGH:1,MEDIUM:2,LOW:3" --board-ref "ADO Iteration 6" --by "Priya Nair"
#    --end YYYY-MM-DD or --days N override the window. --board-ref is a manual mapping; nothing reads it.

# 2. Propose a slate (writes nothing), then confirm it by name.
/sprd-sprint slate --sprint S07
/sprd-sprint slate --sprint S07 --by "Priya Nair" --spec 0007 --spec 0009 --spec 0012
#    Over the target exits 1 unless --override --reason "<why>". A mix breach only warns.
/sprd-sprint unslate --sprint S07 --spec 0012 --by "Priya Nair" --reason "blocked on DL-04 until the vendor answers"

# 3. The daily flow check (read-only, exit 0 always).
/sprd-sprint status --sprint S07
/sprd-sprint status --sprint S07 --wip-cap 2

# 4. Own the wait.
/sprd-sprint handoff --spec 0007 --to "Jordan Baptiste" --by "Priya Nair" --note "needs the eng verdict"
/sprd-sprint ack --spec 0007 --by "Jordan Baptiste"

# 5. Independent verdicts. The front door is /sprd-refine validate (6.3); the verb exists here too.
/sprd-sprint verdict --spec 0007 --lane eng --verdict accepted --by "Sam Oduya"
/sprd-sprint verdict --spec 0007 --lane data --verdict n-a --by "Lin Wu" --reason "no data-bearing change"

# 6. Ready the sprint. Exit 1 and every gap listed if any slated spec falls short; nothing written.
/sprd-sprint ready --sprint S07 --by "Priya Nair"
/sprd-sprint plan --sprint S07                      # re-render the planning page on demand
/sprd-sprint plan --sprint S07 --output /tmp/S07.html

# 7. Close. Kept = merged. Every other slated spec must be carried or dropped by name, with a reason.
/sprd-sprint close --sprint S07 --by "Priya Nair" --carry-to S08 \
  --carry "0009=dependency 0007 merged late" --drop "0012=superseded by FE-04"

Flags common to every verb: --state or --repo (mutually exclusive), --today YYYY-MM-DD for business-day replays, and on write verbs --field KEY=VALUE for an extra ledger key. A field named velocity, points, estimate, effort, hours, capacity, pr_count or loc is refused with exit 2 before anything is written. --json is available on status, the slate proposal, and plan.

The slash command owns the dialogue: it shows the proposal as a table and asks a named human to confirm, and at close it asks about each open spec. For a dashboard, the script's JSON is the same view: uv run scripts/sprint.py status --state .sdlc/state.yaml --sprint S07 --json.

Page:      not yet rendered
ready when: every slated spec is READY with eng accepted and data accepted or n-a

A section with nothing to report reads no data. A mix tier with no target reads no target. A missing WIP cap reads cap not set. The build order is advisory: dependencies first, then the spec that unblocks the most others, then HIGH before MEDIUM before LOW, then spec id. The human picks; the script suggests.

The ready rule

Conjunctive, for every slated spec: DoR READY, status at least ready, eng_review: accepted, data_review: accepted or n-a, no dependency cycle in the slate, no depends_on pointing outside the slate at an unmerged spec. An empty slate is itself a gap. The rule checks only the slate, never gates G1 to G7, and never writes state.yaml.

6.4 The planning and review pages

ready writes .sdlc/reports/sprint-S07-planning.html; plan re-renders it on demand, including before ready so the meeting can run from a draft that still shows the gaps. close writes sprint-S07-review.html. Both are self-contained HTML in the visual language of the phase reports and are linked from .sdlc/reports/index.html when it exists. Sections: header (id, goal, start to end, board ref, readied by), commitment table, mix and capacity, build order and next up, dependencies, one card per slated spec (Goal, Why, acceptance-check count, tier and why, harness context, Decision List), open decisions, carried in, and on the review page the Close outcomes with the ledger's carry and drop reasons. Every empty section reads "no data". The footer always carries: Never tracked: velocity, story points, PR count, lines of code.

6.5 The Sprint view and the Dependency Constellation

g then s opens the Sprint view. It renders sprint.py status --json as-is: the sprint chip (id, goal, state, days remaining or "unknown"), the slate table (spec, name, risk, type, status, DoR, eng, data, next owner), readiness with each spec's gaps, pending verdicts and unacknowledged hand-offs with their business-day age, mix actual against target, WIP against cap, the build order and next up. A button opens the planning or review page. The view has no write verb for slating; those are decisions needing a named human and a reason, which a click would hide.

The Graph / Table toggle shows the Dependency Constellation or the slate table. The Table is the real content, not a fallback, and is what renders when WebGL is unavailable, the window is under 400 px, the canvas has crashed, or the app is under test.
