1. Welcome and opening a project

SDLC Studio is the desktop front end for the claude-code-sdlc plugin. It never reimplements plugin logic: everything it shows is read through the plugin's own scripts, and everything it changes goes through them too. This guide is about the window. The plugin and the slash commands are covered by the setup guide beside this one.

On launch the window reads Loading… while it probes the tools it depends on. If a required one is missing it stops at the tooling screen described in §15; otherwise it opens on Welcome. The code-host CLIs are never required to open a project.

On the Welcome screenWhat it does
New project…Opens the New project screen: a Project name, a Location chosen with Choose location… (remembered for next time), and a preview line, Will create: <path>. Create project makes the folder, starts version tracking in it, and continues into the same set-up wizard an existing folder goes through. You never leave the app to make a folder first.
Open folder…A folder picker. A folder that already holds .sdlc/ opens as a project. One that does not goes to Set up a project here: pick a Playbook (a plugin profile), read the This will create list of directories and files the plugin previews, and press Set up project. If the folder already has a project the wizard says so and creates nothing.
RecentProjects you have created or opened, newest first. Empty, it reads "No recent projects".
⌘K hint"⌘K searches and jumps once a project is open." The palette already works here, with only its actions group: New project…, Open folder…, the appearance toggles and the shortcuts help.
System / Light / Dark pillThe theme, as window chrome. The same three words appear in Settings › Appearance.

Opening a project reads it through the plugin and can take seconds. A card covers the window for that time, Opening <project>… with the subtitle "Reading the project through the plugin." and a running clock, so nothing underneath can be clicked twice. The same card appears for any long plugin-backed action, such as signing off a stage. An error before a project is open is a sticky toast; inside a project it is a banner at the top of the screen, left in place so it can be re-read. A project whose code-host CLI is not ready opens all the same, with an amber banner saying what that costs (§10); Dismiss hides it for the session.

2. The shell: band, strip, stage area, chat

Once a project is open, every screen shares one frame: a thin band across the top, the lifecycle strip under it, the stage area beneath, the chat panel on the right, and a console that docks along the bottom when opened. There is no sidebar. On a narrow window the panes stack vertically.

Band · stripMark and project name · the omnibar trigger (⌘K · a spec id, a verb, or a place) · needs you · sync chip · Console, Appearance, Settings, … · nine stations on a lit rail, Build Loop naming the sprint
Stage areaThe sprint home, planning, a spec card, the lifecycle home, a document, the Board, How it is going, Closing, a spec page, steering mode or Settings — whatever the strip, the omnibar or the palette opened last
ChatA Claude Code session scoped to the stage you are viewing, with its proposed writes shown as cards you accept or discard

The band

Left to right: the mark and the project's name as one button (it leans out to the lifecycle home; the playbook id is its tooltip); the omnibar trigger, a button drawn as a field reading ⌘K · a spec id, a verb, or a place (§4) — never a text box at rest, so nothing on the shell takes typing until you ask; the needs you chip, which is the length of the list the app addressed to you by exact handle (needs you · 2, or the words nothing needs you; signed out it is disabled and says sign in or type your name to see what needs you); the sync chip; and Console, Appearance, Settings and a … menu holding Chat, Keyboard shortcuts, Steering mode, New project… and Open folder….

The lifecycle strip

The strip is the only navigation: the nine stages as stations on one rail, drawn as plain SVG. The lit part of the rail counts finished stages — signed off, or completed with no name recorded — never time. Each station is a button whose description reads the stage's own line; the station whose home you are looking at wears the accent ring. Build Loop reads Build Loop · S08 · 8th sprint when the plugin lists the sprint, Build Loop · S08 when it only knows the id, and Build Loop alone with no sprint; selecting it unfolds Build's views — Home, Planning, Board, How it is going, Closing, Documents. Exactly one entry on the strip is marked as the current page.

Hovering a station lights the same station on the Lifecycle graph of a stage home, so the strip and the graph are one fact. Appearance is a disclosure with the Theme, Density and Animations toggles. The sync chip is a status, not a control; hover it for the detail.

Two homes. A project in the Build loop opens on the sprint home (§3) when the installed plugin knows sprints (sprint-status); every other project — and a Build project on an older plugin, whose Build station then says sprint home arrives with a newer plugin: lacks sprint-status — opens on the lifecycle home (§7). The choice is made once, when the project opens, never on a timer; g s and g l switch between them.

The stage area

Whatever is open: a stage home (§7), a document, one of the Build screens (§8), a spec (§9) or Settings (§12). Each screen keeps its title and primary controls pinned at the top while it scrolls. Esc goes back one level when there is something behind the screen, and never discards an unsaved edit.

The chat panel

The header says Chat and, underneath, what it can see: Helping with: <document> when the stage's workflow has a current document, otherwise Can see: <project>, <phase>. It runs a real, multi-turn Claude Code session against the project, scoped to the stage you are viewing; switching stages switches conversations. Before it is ready, a three-step checklist shows what it is waiting on: Connecting to Claude Code, Reading <project>, Loading <document>.

  • Your words stay as typed. The assistant's replies are rendered as markdown with raw HTML dropped, links never clickable and images never fetched.
  • Structured questions arrive as pills inside the reply. Pick one, or type anything else as the next ordinary turn; the box is never gated on an open question.
  • A proposed write is a card, Proposed write — <document> — <section> — <field>, with Accept, Edit and Discard. Nothing is written to the document until you accept. A discarded draft is still recorded under your name in the plugin's draft ledger. While a card is open the composer reminds you: "A proposal above is waiting on you."
  • The chat does not open documents. It writes into fields of the document it is helping with, once you accept; to read or edit a document yourself, open it from the Workflow or Documents tab. The Workflow tab's Talk it through activity sends one turn through this same panel.
  • Enter sends, ShiftEnter adds a line. The Stop button is drawn disabled with its reason — there is no cancel verb for a turn yet.
  • ⌘\ hides the panel without losing the conversation or a half-typed message; ⌘⇧C focuses the composer. Drag the panel's left edge to resize it (280 px minimum; double-click the edge to return to 380 px).

If Claude Code could not start, the panel says so where the conversation would be, "The assistant could not start.", with the reason, and invites you to type a message to try again or open a document to edit it directly. When the installed Claude Code lacks a flag the app needs, the composer is disabled and its placeholder is the sentence saying which flag and how to update.

3. The sprint home

The command center. A project in the Build loop lands here, and Home under Build Loop (g s) returns to it. Everything on it is a field of sprint.py status --json, spec_status.py --all --json, track_decisions.py --json, record_findings.py report --json, scorecard.py report --json, project_settings.py --json and sprint.py log --json, read once by the app's main process into one document whose every block names its source and the time it was read. The window computes no status of its own; a value the plugin did not give reads no data.

Below the lanes the Dependency constellation keeps its Graph surface, and the slate table — Spec · Name · Risk · Type · Status · DoR · Eng · Data · Next owner · Depends on, with the Readiness, Verdicts pending, Handoffs open, Next up, Dependency gaps, Decisions and Carried in cards and the Planning page / Refresh / Review page buttons — is its Table twin, exactly as before.

Keys in the lanes. With focus inside the board, j / k move across the cards in reading order, ↵ opens the card in place, h opens the hand-off dialog for it, v the verdict dialog, Esc clears. The verdict dialog offers accepted, returned, pending (and n-a on the data lane only, with a required reason); on a spec you built it shows a note — you built this — the verdict is someone else's — rather than a greyed button, because the rule is the plugin's, not the window's. There is no Approve anywhere: the non-author approval belongs to the code host.

The cockpit

The four lanes and the Today column are one cockpit: from 1240 px of width the home gives them the whole first screen — the four wells in one row, Today as a 300 px rail on the right — and sizes that row to the window, so every lane is visible without scrolling at 1440×900 and the wells and the rail end on one line 24 px above the fold. Cards scroll inside a lane; the window itself never scrolls (only the stage area does). What sits under the fold — In the room, Refining, How it is going, the constellation — begins a clear step below, never cut on the edge. Under 1240 px Today becomes a compact strip above the lanes, capped at 120 px with a fade that says "more below"; narrower still, the lanes wrap. The chat starts collapsed to a 40 px rail on the sprint home and on planning so the lanes get the width; the band's Chat button, the … menu row or ⌘\ open it, and the app remembers your choice per screen on this machine. The business-day bar spans the header; a mix short of its target is a measured gap in the header's amber chip, not an error.

Keyboard and the omnibar

The cockpit is built to be driven without the mouse. ⌘K opens the omnibar over whatever is showing (§4): a spec id opens its card, a verb — verdict 0002 accepted, hand 0006 to Sam — previews the exact sprint.py line and opens its dialog, a place name jumps there. Inside the lanes j / k / ↵ / h / v do the work; g p goes to planning and g s back; g t is steering mode; ⌘\ unfolds the chat and ⌘⇧C unfolds it and puts the cursor in the composer. Esc always closes the innermost thing first — a menu, a hover card, a dialog, the palette — and after a verb has run, focus returns to the card you acted on only once the refreshed read has arrived, so what you see under the cursor is the plugin's answer, not a guess. The full table is in §11.

4. The omnibar

⌘K, or the band's trigger, opens the palette. Besides the groups below (§11) it understands a small grammar, resolved only against the specs on the board and the people on the roster — free text never reaches a command line:

The dialog shows the exact line, who it is recorded against and where that identity came from (the roster, the code host, or a name typed for this session), the preconditions the plugin will check, and one Confirm. The answer is the plugin's own stdout and stderr, word for word, under Done (exit 0), Not done (exit 1) or Refused by the plugin (exit 2). Nothing on screen moves until the exit code and a fresh read have both arrived. With nobody signed in the Confirm is disabled — Sign in or type your name — the plugin records who is accountable — and the typed-name form opens in the dialog. A verb the installed plugin lacks is present and disabled: arrives with a newer plugin: lacks <capability>.

5. Sprint planning

Planning under Build Loop (g p). The header is the sprint home's, with Edit goal (sprint.py edit, recorded against you; disabled with its reason on an older plugin) and Edit target · mix · dates present and disabled — those are set at sprint new. Carried in lists what the last sprint's close carried here, with each reason.

  • Refined backlog — the candidates, READY first, then by status, then by id; each row shows its DoR state and gap lines, risk chip, tier confirmation, depends_on and owner. Add to slate is enabled for every candidate, drafts included: the plugin, not the window, lists the gaps when the sprint is readied. refine in place → opens the spec card; Confirm confirms the tier.
  • The slate — the slated specs in the plugin's build order (build_order[]; rows the plugin did not order sit under order not given), each with Builder and Checker pickers over the roster (spec_transition.py assign; the no-self-check rule is the plugin's refusal, shown as it comes), a Security signer picker on HIGH rows that is always disabled with its reason (no frontmatter field exists for it yet), the HIGH rungs quoted from the checking ladder — security pass — blocks, named human sign-off in the PR — and Remove from slate with a reason. The Risk mix meter is three bars, actual over target, beside last sprint's.
  • What the plugin says — the readiness gaps, dependency-order gaps and mix warnings verbatim; The plugin proposes, the deterministic id-order fill from sprint.py slate --json, with Apply proposal (one slate for the whole set, previewed in the dialog) and Claude proposes a reasoned slate disabled with its reason; and Commit the sprint, a dialog that first lists the lines it will run, then runs slate (only if the set changed) → ready → plan → opens the planning page → one decision per unconfirmed tier when the plugin can confirm tiers, stopping at the first non-zero exit and showing each step's answer. Over the target, it asks for the --override reason.

The Slate / Proposal toggle above the columns switches the constellation between the committed set, drawn in build order, and the proposed set, drawn with no order and the caption order arrives when the slate is committed.

6. The spec card

A lane card (↵ or click) or a Refining row's refine in place → opens the spec card in place; Esc or ← Back to the board returns and hands focus back to whatever opened it. One read, getSpecCard, runs spec_readiness.py --spec --json (with the ladder), spec_status.py --spec --json, record_findings.py report --json --spec, check_channel.py --json when a channel is bound, and handoff.py --check when a developer is named; each block names its source.

ZoneReads
HeaderId and name, the risk and status chips, the channel and team, Owns it / Builds it / Checks it as rings, the path, the pull request or no PR yet, the review verdicts.
Intent · Definition of ReadyThe Risk tier with Confirm (when the plugin can) and the existing raise / lower controls — raising is free, lowering asks for the name it is recorded against — under the fixed sentence Raising a tier adds rungs for free; lowering is recorded against whoever decided and the spec's own Why this tier note. Then Still needed, Worth a look and Passing, the checker's messages verbatim; Claude proposes a rewrite on an advisory is present and disabled with its reason. Then Scope — In, Out and harness_context read from the document itself — and the channel's acceptance dimensions when one is bound, or no channel bound.

A disc is green, red or blue only from the host's own conclusion; a rung with nothing to read is a hollow ring beside no data, and correctness is always that. On an older plugin without the dry run the button is enabled and the live refusal lands after, in the plugin's words.

7. A stage home (the lifecycle home)

Selecting a station on the strip (or [ / ], or g then a digit) opens the lifecycle home for that stage: the Lifecycle band, the stage's title and description, three tabs, and — beside them on a wide window, above them otherwise — the same Today column as the sprint home with two groups of its own: Claude is working the <stage>, the app's own record of the chat's activity, labelled as such, and Decisions this week, every open decision with its owner and clock, red only when the plugin says overdue; with no decision log it reads no data — no decision-log. Leaning into the Build station adds Go to the sprint home →. Opening a different stage, or a different project, always lands on Workflow.

The Lifecycle graph

The band above the title is a figure with a Graph / Table toggle and a chevron that collapses it; the collapsed state is remembered on this machine. Its caption is the legend, and the legend is exact:

Nine stages in the plugin's order; the lit rail counts finished stages — signed off, or completed with no name recorded. Height and depth carry no meaning.
  • The rail is lit from the start to the last signed-off station, flat from there to the current station, and dashed beyond it. Lit length is a count of finished stages, never time; stations are equally spaced because time is not a length. There is no gradient between stations, because the plugin reports no progress between them.
  • The current station pulses three times when the screen opens and then stops. The Build station is drawn as a loop, because Build is continuous.
  • Hovering a station, or its plate, expands the plate: the stage's name; its state (Signed off, Completed, Current, Later); Signed off by <name> or no name recorded; Entered and Completed dates for stages that have been reached; N artifacts; and for Build, its five views. Activating a plate goes to that stage, exactly as its station on the strip does.
  • The Table is a list of the same nine rows — Stage · State · Signed off by · Entered · Completed · Artifacts — grouped the same way, with a Now badge on the current row. It is the real content, not a fallback, and it is what renders when hardware graphics are unavailable or the figure is narrower than 640 px.
  • A partial arc on the current station shows complete of total documents, and only when both numbers are known. Nothing is drawn from a guess.

Workflow, Documents, Guide

TabShows
Workflow (1)One step per required document, in the stage's own order, then a Sign-off step. Each step is Complete, Current or Locked; the status comes from the same readiness read the Documents tab uses. The right-hand panel shows the current document's real content, re-read every two seconds while this tab is visible, with ← Back to Workflow, Previous, Next and Edit above it. Before the file exists it reads "Not started yet — this will appear here as soon as it is created." Under the steps, Also in this stage lists the optional activities the plugin declares for the stage, each with one control: Create to start documents from their templates, a check to run, Talk it through to send a turn to the chat, or Open for a panel such as the phase report, intake, review or the Build sprint summary. A blocked activity shows the plugin's reason instead of a control. On Foundation, a Pipeline evidence panel also appears (below).
Documents (2)The files in the stage's .sdlc/artifacts/<slug>/ with a chip each: Not started, N to fill, or Complete. A row opens the document; a folder is listed but cannot be opened as one document. What is missing lists every unfilled field as a sentence (<field> in <section> — <document>) with the plugin's reason; choosing one opens the document scrolled to that field, marked "You were sent here to fill in <field>." Then the sign-off questions, and a banner: "Every required document is present and complete." or "N document(s) still need work before this stage can be signed off.", followed by Signed off by <name>. once it is.
Guide (3)The plugin's phase definition for this stage, rendered as markdown, and Everything you can do in this stage: every activity the plugin declares with its slash command, including the ones the Workflow tab draws no control for. A stage with no definition file says "No guidance file for this stage".
Pipeline evidence (Foundation only)

Foundation closes only when the delivery rails are proven, not merely present. Gather pipeline evidence reads the code host's own run history (it can take up to a minute; a clock counts) and reports each rail as Proven, Ran, never caught anything, Never fired, Broken or No data — the last drawn dashed, because it is the absence of a reading, not a bad one. A rail with no data shows no run count at all. Not yet proven lists what would prove each remaining rail; each of those opens a real pull request, so they are listed here and never run from here. Open pipeline-proof.md opens the document the gather wrote. Read-only: nothing is opened, merged or changed.

Reading and editing a document

A document opens with its file name, description and repository path at the top, and two buttons: History and Edit. Outside edit mode nothing that changes content is on the screen — not disabled, absent. Edit is disabled, with the reason in its tooltip, when the document has no shape the plugin knows ("This document has no shape, so its fields cannot be edited here."); such a document is shown as plain text, and the notice says nothing is hidden.

  • Sections are cards; each field is a term and its value. An unfilled field reads Empty; a field the shape declares but the document lacks reads Not in this document.
  • In edit mode every field gets an editor with Save field (or ⌘S for the editor that has focus) and Revert, plus a button that asks Claude for a draft. The draft arrives as a card, "Claude's draft — review before accepting", with Use this and Discard; it is a proposal until you use it. A saved field shows a toast naming the field, and the stage's readiness is re-read.
  • Documents with numbered sections gain an add control, only in edit mode, that shows the number it will use before anything is created: Add FR-013. While the plugin is working it out the button says so rather than guessing.
  • A notice, Changed since you last looked, lists who changed what and why since your last visit. Opening the document does not clear it; Mark as seen does.
  • History lists every saved version with who saved it and why, compares any version with the latest, and offers Restore. A restore is preview-then-confirm — you see the exact diff and confirm that diff — and it adds a version rather than removing any, which is why the confirmation says Restore as a new version. It is recorded against a signed-in person.
  • Alt↑ / Alt↓ step to the previous or next document of the stage; ← Back to the stage returns to the home.

Signing off a stage

The sign-off step shows Questions for whoever signs this off: a checkbox per question and, beside it, a pre-check of what the app could see — Looks done, Not yet, or Needs your judgement. A pre-check never ticks a box. Only a signed-in, named person can tick one, and each confirmation is recorded as Confirmed by <name> · <time>; the count reads n of m confirmed.

The sign-off card itself appears only when all three hold: this is the project's current stage, every required document is complete, and every question is confirmed. It is titled Sign off <stage>, carries a Signed by field prefilled with your name, and an optional list of discipline sign-offs (Discipline / Section / Signed by, the same triple /sdlc-next offers). Sign off and advance does what /sdlc-next does: checks the seven gates, drafts and validates the phase summary, snapshots the artifact record, and advances.

  • It fails closed. A refusal is shown in the plugin's own words, whole, naming the gate or step it stopped at; the button becomes Try again. Nothing is advanced until the plugin says yes.
  • On success the card reads Signed off — moved from Phase X to Phase Y, a toast and a live-region announcement record Phase X signed off · by <name>, and the Lifecycle rail plays a short ceremony to the stage just signed. The end state equals a cold reload.
  • Completed versus Signed off. The plugin's state records only that a stage's status is completed; the name is recorded separately. A finished stage is called Signed off only when a name is on it. One finished without a name reads Completed · no name recorded, on the strip, on the graph and in the table alike.
  • If the installed Claude Code lacks a flag the app emits, the button is off and the reason is printed beside it: drafting the phase summary is a model call that would fail after the gates passed.

Build Loop is the exception. Its home shows a card, Build ends from Closing, with a Go to Closing button: Build is declared complete from Build › Closing once every spec is decided and each team has confirmed its list (§4), and the generic sign-off is refused for it.

8. The Build Loop's other views

Selecting Build Loop on the strip unfolds its six views — Home (§3), Planning (§5), Board, How it is going, Closing, Documents — reachable with g then s / p / b / h / c / d. Every number on these screens is the plugin's. The app computes no status of its own, and a value the plugin reports as null reads no data, never 0.

9. A spec page

The Board opens a spec as this page; the sprint home and planning open the spec card instead (§6). The two share their words — Owns it, Builds it, Checks it, ← Back to the board — and the same raise / lower controls for the tier. The page's Sprint decisions slots (hand off, acknowledge, remove from the slate) open the omnibar's dialog with the line pre-filled.

A spec opens from a Board row, a slate row, a constellation plate or the palette's # group. Its order is deliberate: who, then is it ready, then where is it, then what checked it, then what you cannot do yet.

  1. Who. Owns it, Builds it, Checks it, Risk. An empty role reads nobody. The checker is never the same person as the developer; the plugin refuses that at hand-off.
  2. Readiness (shown while the spec is not yet in flight or merged). Ready, the card reads Ready to hand off. with a Hand off button. Not ready, one amber notice reads N things still needed before this can be handed off. and lists them under Still needed. A draft spec also offers Mark ready, which is shown even when it will be refused — the refusal comes back with its reasons, and hiding the button would hide the rule.
  3. Risk tier. LOW / MEDIUM / HIGH, with the sentence "Raising a tier is free. Lowering one is recorded against whoever decided it." Lowering is refused until a name is given in the field that appears, "Who authorised lowering this tier? Written into the spec." The name is never pre-filled or remembered: each downgrade is a deliberate act with somebody's name on it.
  4. Worth a look. Advisory findings, chiefly the vague-line lint on acceptance checks. "These do not stop a hand-off. A flagged acceptance check is a hint that two people could build different things from it — whether that is true is a judgement, not a pattern match."
  5. N checks already passing, behind a disclosure.
  6. The pull request, read from the code host (Reading the pull request on GitHub… or … on Azure DevOps…). No pull request yet reads "No pull request yet. This spec has not been handed to anyone." with the branch name. With one: Open, Merged or Closed without merging, its number, Open on the code host (the only link out, because the checking happens there), and the plugin's waiting-on sentence. Then one card: Checks with a dot and chip per check (running, success, or the host's conclusion; a completed check with no conclusion is unknown, never red); The grader with its per-check verdicts and the line "The grader advises. It never blocks a change on its own." (a grader that ran but could not be read is said plainly, in amber, and is not a pass); Security review when the tier requires one; Approvals by name and date. When the host cannot be reached the notice reads Could not reach the code host. and The spec file itself says <status>. — a claim about the app, never "not started", which would be a claim about the work.
  7. Sprint decisions. Verdict, Pass next action, Acknowledge, Mark ready are drawn disabled with the reason: these arrive with the plugin's sprint write verbs. Until then they are recorded with /sdlc-sprint and /sdlc-refine.

The hand-off dialog

Hand off <id> replaces the spec page inline. It restates the three roles, then asks for the Developer as an @handle; the hand-off command checks the handle against the roster. The dialog enforces nothing itself: it asks the plugin and shows the answer. A refusal is headed in plain language from its kind — This spec is not ready to hand off yet, That person is not on this project, That person is already checking this change, That team is at its limit — with the plugin's message underneath. Only after a team-at-limit refusal does a reason field appear, "Why are you going past the limit? This is written into the record.", and the button becomes Hand off anyway. Success reads Handed off (or Already with a developer) with the developer, the checker, the branch and Pull request opened.; Back to the board returns to a re-read board. If the branch and commit were made but the host could not be told, an amber notice says so and asks you to assign it by hand. Typed text in this dialog counts as unsaved work: Esc stops here.

10. Working with the code host

The repository chooses its host by its origin remote: a GitHub remote means the GitHub CLI (gh); a dev.azure.com, *.visualstudio.com or ssh.dev.azure.com remote means the Azure CLI (az) with its azure-devops extension. A pin in .sdlc/code-host.yaml or the SDLC_CODE_HOST environment variable overrides the remote; an unrecognised remote is host none, where pull-request features are off and gh is tried as before. The app probes the CLI's state once per poll interval; it never guesses "not signed in" when a probe did not run.

Settings › Repository shows what was detected: a Code host row, GitHub or Azure DevOps with where that came from (the origin remote, the pin file, or the environment variable); a CLI row that reads az — signed in as sam@corp.com (roster: @sam-k), gh — typed for this session: Sam K, gh — sign-in not checked yet, or the reason it cannot say; and the other CLI as not needed for this repository. In edit mode, Pin the code host (GitHub / Azure DevOps / none) writes .sdlc/code-host.yaml through the plugin's own set_setting.py code-host; the file travels with the clone and is read ahead of the remote.

Signing in, and who the app thinks you are

Sign in outside the app — gh auth login, or az login after az extension add --name azure-devops — then press Refresh on the screen you are on. Your identity is resolved in order of trust: the roster handle that matches the signed-in identity (a GitHub login is the handle; an Azure DevOps sign-in identity matches a person's email: in .sdlc/team.yaml, and nothing else), else the identity itself. It is shown in Settings › Repository as Signed in as, and it is the name every sign-off, confirmation, restore, draft decision and save is recorded under.

The typed-name fallback. Only when the host cannot say who you are — signed out, or Azure DevOps with a PAT alone — does the app offer Sign in as a typed name — under Signed in as in Settings › Repository, and in the hand-off dialog. The name must be 2 to 80 characters on one line, and a name that reads as an AI or automation is refused with the reason. It is held for this session only, never saved to disk; the connection records its source as typed, and the app's own commits carry the suffix (typed name). The moment the host can identify you the typed name is forgotten, and offering one while the host already knows you is refused: "GitHub already identifies you as <login>; a typed name is only for when it cannot."

14. Honesty rules the app follows

  • The lit rail counts finished stages. Signed off, or completed with no name recorded. Never time, never a percentage of the way to the next station.
  • No status is computed in the window. Readiness, verdicts, build order, alarms and scorecard figures are the plugin's. The only thing the app works out is "is this waiting on me", a comparison of handles the plugin supplied.
  • "no data" over zero. A value the plugin did not measure reads no data with the sentence saying what would produce some. Nobody-has-merged-anything and everything-was-rejected are opposite situations; a 0 would show them identically.
  • No activity metrics. Velocity, story points, pull-request counts and lines of code are not shown anywhere, and the plugin refuses to record them. Nothing is totalled per person.
  • Disabled controls always say why. The reason is in the tooltip and read to assistive technology. A control that is hidden rather than disabled is hidden because it would be refused — and the refusal, when you reach it, is the plugin's own words.
  • Amber is a notice, not an error. NOT READY, a team at its limit, a dependency gap and a review over its alarm are amber. Red is reserved for hard failures: an unreachable host, a refusal, a non-zero exit, stderr.
  • Named humans. Every sign-off, confirmation, restore, declaration and save is recorded under a signed-in or typed name, and a name that reads as an AI is refused.
  • Prose stays prose. The plugin's sentences — dependency gaps, waiting-on lines, blocking reasons — are shown as text and never turned into geometry or colour.
  • The plugin is the only source of truth. The window never runs a script of its own accord and never joins two sources into a status: the main process reads one document per project, each block naming the script it came from and when, and every write is one line from a closed table — sprint.py <verb> … --by <you> — shown before it runs and answered in the plugin's own words under Done, Not done or Refused by the plugin. Nothing on screen moves until the exit code and a fresh read have both arrived.
  • Presence, never totals. In the room shows dots per lane, not counts per person; needs you is the length of a list addressed to you, not a score.
